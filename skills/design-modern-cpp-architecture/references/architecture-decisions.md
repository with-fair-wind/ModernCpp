# 架构驱动因素与决策记录

用本参考把模糊目标转化为可验证设计，并生成足以支持评审和演进的最小文档。

## 质量属性场景

按以下六项描述架构驱动场景：

1. **触发源**：用户、设备、外部系统、运维人员或故障。
2. **刺激**：请求、负载变化、依赖失效、配置变更或攻击。
3. **环境**：正常、峰值、降级、启动、升级或恢复期间。
4. **对象**：受影响的服务、组件、数据或基础设施。
5. **响应**：系统采取的可观察行为。
6. **指标**：延迟分位数、吞吐、丢失率、恢复时间、资源上限等。

示例：“采集线程在峰值 1 kHz 输入下投递帧完成事件；显示消费者阻塞 200 ms 时，采集路径不得阻塞，内存增长不超过 64 MiB，系统丢弃旧显示帧并记录计数器。”这个场景会直接决定队列边界、容量与溢出策略。

## 结构与动态视图

- **系统上下文**：用户、外部系统、信任边界和系统职责。
- **可部署单元/进程**：进程、服务、数据存储及其协议。
- **组件**：进程内主要职责、提供/需要的端口和依赖方向。
- **动态视图**：关键用例、并发交互、超时、失败和恢复路径。
- **部署视图**：节点、进程、资源限制、网络区域和可用性策略。

C4 的系统上下文图和容器图（Container Diagram）通常已足够；这里的 Container 指应用、数据存储等可独立运行或部署的单元，不特指 Docker 容器。不要为了完整度机械绘制所有层级。图中标明关系名称、方向、协议和关键语义，避免“Manager”“Helper”“Common”这类无法说明职责的名称。

## 边界检查

对每个组件回答：

- 它拥有哪类状态，谁能修改？
- 它提供什么稳定能力，而不是暴露什么内部类？
- 哪些变化应被隔离在该边界内？
- 是否需要独立部署、测试、版本化或替换？
- 跨边界传递的是值、不可变快照、句柄还是借用视图？
- 边界失败会如何传播、隔离和恢复？

如果两个“组件”总是同时修改、同时部署、共享大量内部状态且无法独立测试，边界可能是人为切割。反之，若一个组件同时处理领域策略、线程调度、序列化和设备 SDK，边界可能过宽。

## ADR 最小内容

一份 ADR 只记录一个重要决策：

- 状态：proposed、accepted、deprecated 或 superseded；
- 背景与问题；
- 决策驱动因素；
- 候选方案；
- 决策与理由；
- 正面/负面后果；
- 验证方法；
- 替代或回滚条件。

不把 ADR 写成会议纪要，也不隐藏缺点。无法逆转、跨团队、改变公共接口/协议、引入重要依赖或改变并发模型的决策优先记录。

## 演进与迁移

优先设计可分阶段验证的迁移：

1. 建立契约测试和观测基线。
2. 在旧实现前建立端口或适配层。
3. 按用例或消息类型迁移，不做不可回滚的大爆炸替换。
4. 允许受控双写/影子运行时，明确一致性和清理条件。
5. 达到退出标准后删除旧路径和临时兼容层。
