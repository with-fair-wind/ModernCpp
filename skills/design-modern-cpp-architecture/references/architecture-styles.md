# C++ 系统架构风格

架构风格决定粗粒度边界和交互约束；设计模式解决边界内部或边界之间的局部问题。先选择最少的必要约束，允许不同子系统采用不同风格。

## 模块化单体

默认从单进程、模块化单体开始：组件有显式 API 和依赖规则，但共同构建、部署和观测。它减少网络协议、分布式一致性和运维成本，适合大多数桌面、设备、工具和中小型服务。

模块化单体不是“所有代码互相 include”。使用独立构建目标、公共/私有头文件、依赖方向测试和组合根维护边界。只有独立部署、故障隔离或组织自治产生足够价值时再拆进程/服务。

## 分层架构

适合依赖方向清晰、请求从接口层流向应用和领域层的系统。常见层次：表现/传输 → 应用用例 → 领域/核心 → 基础设施适配。

避免：

- 每层只是把相同 DTO 和函数透传到下一层；
- “common” 层依赖所有层；
- 领域层包含线程、数据库或 SDK 细节；
- 任意跨层调用破坏规则。

允许性能关键路径在有证据时使用专门端口绕过通用层，但记录并测试例外。

## 端口与适配器

适合核心策略需独立于设备、网络、存储、GUI 或第三方库测试的系统。核心定义它需要/提供的窄端口，外围适配器实现协议转换和资源管理。

不要为每个函数创建纯虚接口。端口应对应稳定业务能力或外部边界。编译期可替换且不会跨 ABI 时可用 concept/template 端口；运行时替换或测试替身需要稳定接口时使用虚接口/类型擦除。

## Pipeline 与数据流

适合图像、音视频、编译、ETL、信号处理和批量变换。把处理拆成有明确输入/输出、所有权和并发度的 stage；图结构可以是线性 pipeline 或 DAG。

必须定义：

- buffer 所有权、复用和对齐；
- stage 并发度、排序和批量；
- 队列容量、背压和丢弃；
- 错误是否停止全图、隔离单项或进入旁路；
- flush、drain、取消和关闭。

ranges 适合同线程惰性值流；Taskflow/oneTBB 适合任务图；Boost.Asio/actor 适合长期异步 agent。不要把它们混称为同一种 pipeline。

## 事件驱动

适合多个组件对事实变化作出独立反应。事件应表示已发生事实，发布者不依赖订阅者成功完成。

事件驱动会降低静态耦合但增加时间耦合、顺序、重试和观测复杂度。进程内同步事件与跨进程持久事件差异巨大，应使用不同端口和消息类型。核心业务不变量通常应在单一事务/用例内维护，而不是依赖不确定顺序的多个订阅者。

## Actor

适合大量并发状态所有者、消息驱动协议、监督和故障隔离。每个 actor 独占其可变状态，通过 mailbox 处理消息。

评估 mailbox 容量、调度公平性、消息复制、请求超时和 actor 生命周期。不要创建细粒度 actor 导致调度/消息成本超过业务工作，也不要在 actor 外泄漏内部可变对象引用。

## ECS 与数据导向

适合同构实体数量大、系统按组件批量遍历、缓存局部性重要的游戏、仿真和可视化场景。ECS 不只是“用 EnTT”；它改变数据组织、行为归属、生命周期和查询方式。

不适合以复杂不变量、长生命周期对象协作和少量异构实体为主的普通业务模型。通过基准确认 SoA、group/view 和并行系统调度的收益。

## 插件架构

适合部署后发现扩展、供应商模块或独立发布功能。设计稳定的 host/plugin 协议：版本协商、能力发现、创建/销毁、错误、线程、回调和卸载。

编译期插件列表只是 policy/注册表，不需要动态库复杂度。动态插件优先 C ABI + 不透明句柄；同工具链内部可使用窄 C++ 接口，但仍需版本和卸载测试。

## 多进程与服务

拆分依据应是部署、故障、安全、资源或团队边界，而非类数量。进程边界带来序列化、延迟、部分失败、身份、观测和版本兼容。

嵌入式/桌面系统可用辅助进程隔离不可信插件或易崩溃 SDK；服务端可按独立扩缩和数据所有权拆分。若两个服务必须同步发布、共享数据库表并在每次请求中多次往返，它们可能不是独立服务。

## C++ 物理边界

- 一个架构组件通常对应一个或少量 CMake target，而不是仅对应命名空间。
- 公共头只暴露稳定 API；实现头放在 `detail/` 或 target 私有目录，但 `detail` 不是安全/ABI 边界。
- 使用 `PRIVATE/PUBLIC/INTERFACE` 依赖表达传播关系，避免目录级全局 include/link 设置。
- C++20 modules 可减少文本包含和表达导出边界，但不会自动修复循环依赖、ABI 或职责混乱。
- 模板定义传播给消费者；需要隐藏实现或稳定 ABI 时使用显式实例化、Pimpl、类型擦除或 C 接口。
- 跨 target 的生成代码、配置宏和编译选项应由明确接口 target 管理，避免 ODR/ABI 不一致。

## 选择顺序

1. 先确定部署单元和故障隔离需求。
2. 在每个进程内确定状态所有权与并发模型。
3. 按业务能力划分组件，建立单向依赖。
4. 对外部技术使用端口/适配器。
5. 对计算流程选择直接调用、pipeline、事件或 actor。
6. 最后才为局部变化轴选择设计模式和 C++ 多态机制。

组合示例：模块化单体 + 端口适配器作为总体结构；图像处理子系统采用有界 pipeline；GUI 通知使用同步 signal；网络 I/O 使用 Asio executor。无需强迫整个系统只使用一种风格。
