# 架构评审清单

按证据审查，不按模式数量或个人偏好评分。

## 驱动因素

- 是否明确范围、利益相关者、约束和关键假设？
- 质量目标是否写成可测场景，并有优先级？
- 候选方案是否针对同一组驱动因素比较？

## 边界与依赖

- 组件是否按职责与变化原因划分，而非按技术名词堆叠？
- 领域策略是否依赖 UI、数据库、传输、设备 SDK 或具体框架？
- 公共接口是否表达能力和稳定契约，而非暴露内部对象图？
- 是否存在循环依赖、万能 Manager/Common、Service Locator 或隐式全局状态？
- 跨 ABI/插件边界是否有版本、分配和销毁规则？

## 所有权与生命周期

- 每个服务、任务、订阅、buffer 和线程由谁拥有？
- 借用视图的有效期是否可证明？
- `shared_ptr` 是否确实表达共享所有权，而非逃避设计？
- 启动、部分启动失败、正常关闭和强制关闭顺序是否定义？

## 并发与异步

- 线程安全是对象级、操作级还是用法约束？
- handler 在哪个执行上下文运行，是否允许并发和重入？
- 队列是否有界，慢消费者和过载策略是什么？
- 超时、取消、重试、幂等与故障传播是否分开建模？
- 是否在持锁期间调用未知用户代码？

## 数据与消息

- 命令、事件、查询、任务和传输消息是否语义清楚？
- 消息是值、不可变共享对象还是借用？
- 顺序、重复、丢失、版本和 schema 演进是否定义？
- 高频大对象是否有内存、复制、批处理和保留预算？

## 模式与 C++ 机制

- 模式解决了哪个已识别变化轴？
- 类型集合开放/封闭、替换时机和 ABI 是否支持所选多态？
- `concept` 是否表达语义，模板是否造成不必要传播或代码膨胀？
- `variant`、类型擦除、虚接口和直接值类型是否做过比较？
- C++23 特性是否降低非法状态或样板，并受目标工具链支持？

## 框架与公共库

- 是否先评估标准库和成熟开源实现？
- 依赖的许可证、治理、版本、构建和退出路径是否可接受？
- 第三方类型是否被限制在适配器后？
- 自研公共框架是否已有两个独立消费者和维护承诺？

## 安全、韧性与可运维性

- 是否标明信任边界、不可信输入、身份认证、授权和最小权限？
- 密钥、凭据、个人信息和敏感业务数据如何存储、传递、轮换与清理？
- 插件、动态库和第三方依赖是否有来源验证、版本约束、签名或隔离策略？
- 队列、消息、连接、请求和日志是否有大小/速率上限，能否抵御资源耗尽？
- 依赖失败、进程崩溃、部分启动、升级失败和数据损坏时如何降级、恢复或回滚？
- 健康检查、日志、指标和追踪是否足以定位故障，并避免泄漏敏感信息？
- 运维操作是否可审计，危险操作是否有授权、确认和幂等保护？

## 证据与演进

- 是否存在契约测试、依赖检查、压力测试、故障注入或基准？
- 性能结论是否包含硬件、负载、分位数和资源上限？
- 关键决策是否记录 ADR，包含负面后果与替代条件？
- 迁移是否分阶段、可观测、可回滚并有删除旧路径的条件？

## 问题等级

- **缺陷**：已违反明确需求或存在可复现安全/正确性问题。
- **高风险**：关键契约缺失，可能导致严重故障，需原型或决策。
- **权衡**：方案可行但牺牲某项质量，应在 ADR 中显式接受。
- **改进**：不阻碍当前目标，但能降低维护或理解成本。

评审结论应引用具体场景、依赖、代码或实验；没有证据时标为待验证风险。
