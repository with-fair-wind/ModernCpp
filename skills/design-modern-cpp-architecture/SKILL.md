# 设计现代 C++ 架构

根据问题范围选择最短工作路径。把设计模式视为描述变化、协作和扩展问题的一等设计工具；保留模式意图，再根据 C++23、类型集合开放性和运行时约束选择实现。仅在系统级问题中执行完整架构流程。

## 遵循核心原则

- 先明确架构驱动因素，再讨论模式、库和 C++ 特性。
- 保留经典模式的设计意图，不因存在 `variant`、concept 或 callable 就否定模式；区分模式与具体实现技法。
- 让依赖指向稳定策略：领域/核心层不依赖 UI、网络、数据库、设备 SDK 或具体线程设施。
- 明确所有权、生命周期、线程亲和性、同步/异步边界、失败与取消语义；不要只画类关系。
- 优先值语义、组合、强类型接口和构造函数注入。只在确有开放扩展轴时引入运行时多态。
- 以 C++23 为基线，但只在能改善约束表达、所有权、错误通道或实现复杂度时采用新特性。
- 先比较标准库和成熟开源实现，再决定自研；不要为了减少一个依赖而承担隐蔽的并发、ABI 或协议维护成本。
- 把可复用性建立在稳定契约和验证结果上，而不是把项目内部工具直接改名为“框架”。

## 根据任务选择最短路径

先判定任务类型，只读取和执行必要部分：

| 任务 | 执行路径 |
|---|---|
| 解释、选择或现代化单个经典模式 | 读取 [classic-patterns-cpp23.md](references/classic-patterns-cpp23.md)；回答模式意图、适用条件、实现选择、权衡和误用，不执行完整架构流程 |
| 设计 policy、mixin、CRTP、concept 或类型擦除 | 读取 [generic-and-static-patterns.md](references/generic-and-static-patterns.md)，只分析变化轴、约束和成本 |
| 设计新系统、模块边界或重大重构 | 执行下方完整工作流，并按需读取架构参考 |
| 设计事件总线、消息通道或异步通信 | 先读取 [event-messaging.md](references/event-messaging.md) 定义运行时语义；需要选库时再读取 [reusable-frameworks.md](references/reusable-frameworks.md) |
| 设计 State/FSM 模型 | 读取 [classic-patterns-cpp23.md](references/classic-patterns-cpp23.md)，先区分 GoF State、有限/分层状态机和持久化工作流 |
| 选择状态机、任务、actor、插件或其他第三方框架 | 在明确模型与必需语义后读取 [reusable-frameworks.md](references/reusable-frameworks.md)，形成针对性决策记录 |
| 审查现有设计或 PR | 读取 [review-checklist.md](references/review-checklist.md)，报告可验证问题，不默认重新设计系统 |

不要因为 skill 包含完整资料就全部加载。简单模式问题通常只需确认变化轴、开放/封闭类型集合、替换时机、所有权和 ABI，不要求输出 C4 视图、ADR 或迁移计划。

## 执行完整架构设计工作流

仅对系统设计、模块边界、重大架构重构或公共框架抽取执行本节。局部模式选择跳过无关步骤。

### 1. 确认任务与约束

识别任务是新架构设计、现有架构评审、局部架构重构、公共框架抽取还是第三方选型。读取仓库说明、构建配置、部署方式、现有依赖和关键调用链，并记录：

- 业务能力、系统边界、外部参与者和信任边界；
- 目标平台、编译器、C++ 标准、ABI/插件兼容要求；
- 延迟、吞吐、内存、启动时间、二进制大小、实时性和功耗约束；
- 线程模型、进程模型、I/O 模型、故障恢复和升级方式；
- 团队规模、交付节奏、依赖政策和长期维护责任。

信息不足时标注假设与待确认项，不用未经验证的假设填满设计。

### 2. 写出可验证的架构驱动因素

把“高性能”“可扩展”“线程安全”等形容词改写为场景：触发源、刺激、运行环境、受影响组件、期望响应和可测量指标。按业务价值与技术风险排序，选出少量最能改变设计的场景。

需要系统化质量属性、边界图和 ADR 方法时读取 [architecture-decisions.md](references/architecture-decisions.md)。

### 3. 建立当前模型与候选边界

对现有项目先画真实依赖和关键运行时序，再提出目标结构。至少区分：

- 领域/核心策略；
- 应用编排与用例；
- 端口、适配器和基础设施；
- 进程、线程、执行器与外部系统；
- 跨切面策略，例如日志、指标、配置、安全和错误映射。

只画能帮助当前决策的视图。通常先使用系统上下文、可部署单元/进程和组件视图；涉及异步、生命周期或故障传播时补充动态时序图。需要比较分层、端口与适配器、pipeline、actor、事件驱动、插件或多进程服务时读取 [architecture-styles.md](references/architecture-styles.md)。

### 4. 选择依赖方向与变化轴

为每个边界回答“什么会独立变化、由谁拥有、在哪里替换、是否跨线程/进程/ABI”。根据变化轴选择机制：

| 需求 | 首选机制 |
|---|---|
| 封闭且较小的类型集合 | 值类型、`std::variant`、`std::visit` |
| 编译期替换且性能敏感 | `concept`、模板策略、自由函数/定制点 |
| 运行时替换且接口稳定 | 抽象接口或类型擦除 |
| 仅需要保存可调用任务 | `std::move_only_function` 或适配后的 callable |
| 隔离编译依赖或稳定二进制边界 | Pimpl、C ABI、显式版本化接口 |
| 跨线程或跨进程协作 | 显式消息/任务协议，不共享可变对象图 |

不要把 CRTP 称为动态多态，也不要假设模板天然更快；评估代码膨胀、编译时间、诊断质量和 ABI 影响。

### 5. 保留模式意图并选择实现形态

先说明模式要解决的变化或协作问题，再选择实现。不要把经典模式等同于虚继承类图，也不要把新语言特性等同于新的模式。现代化经典模式时读取 [classic-patterns-cpp23.md](references/classic-patterns-cpp23.md)；设计 policy、mixin、CRTP、concept、类型擦除或编译期注册时读取 [generic-and-static-patterns.md](references/generic-and-static-patterns.md)。

选择实现形态时重点检查：

- 类型集合是开放还是封闭，类型与操作哪一侧变化更频繁；
- 替换发生在编译期还是运行期，是否需要运行时发现或热插拔；
- 对象采用值语义、唯一所有权、共享所有权还是非拥有借用；
- 是否需要双分派、状态迁移、通知、请求响应或算法骨架等特定协作语义；
- 接口是否跨编译单元、动态库、进程或不一致工具链的 ABI 边界。

根据这些维度选择直接值类型、组合、泛型、`variant`、类型擦除或虚接口；不要仅因某种机制较新就重写稳定模式。

### 6. 设计跨组件通信

先区分直接调用、信号/观察者、进程内事件、命令/查询、异步邮箱和跨进程消息。不要用一个 `EventBus` 名称掩盖不同保证。

涉及事件消息框架时必须读取 [event-messaging.md](references/event-messaging.md)，明确订阅生命周期、派发线程、重入、顺序、异常、队列容量、背压、取消和停机语义。将 1mZGG 的类型化事件总线视为可借鉴案例，不视为默认答案。

### 7. 评估自研与开源框架

需要信号/槽、事件分发、异步 I/O、actor、状态机、任务图、依赖注入或插件时读取 [reusable-frameworks.md](references/reusable-frameworks.md)。至少比较：

- 需求语义是否真正匹配；
- 生命周期、线程安全、背压、取消和错误保证；
- API/ABI 稳定性、平台支持、发布节奏和维护活跃度；
- 许可证、依赖树、构建集成、编译时间和二进制成本；
- 可观测性、测试设施、故障注入和迁移退出路径。

优先包装第三方库于项目端口之后，避免让领域模型、公共协议和大部分业务代码依赖具体框架类型。

### 8. 完成接口与运行时契约

对每个公共接口和消息定义：

- 所有权、借用范围和对象失效条件；
- 前置/后置条件、不变量与错误模型；
- 线程安全级别、线程亲和性和允许的重入；
- 同步阻塞、异步完成、超时、取消和停机行为；
- 消息排序、幂等、重复、丢失和版本兼容策略；
- 性能预算、分配策略和批处理边界；
- 日志、指标、追踪和诊断上下文。

使用 `std::expected<T, E>` 表达调用方通常需要处理的可恢复失败；不要把所有失败都塞进字符串。协程只改变异步代码的表达方式，不自动提供调度器、背压或结构化并发。

### 9. 形成可审查的交付物

按需复制 [architecture-design-template.md](assets/architecture-design-template.md) 和 [adr-template.md](assets/adr-template.md)。交付物应包含：

- 范围、假设、约束和优先质量场景；
- 当前结构与候选结构、依赖规则和关键动态流程；
- 模式/框架选择及被拒绝方案；
- 所有权、并发、错误、消息和部署契约；
- 风险、验证计划、迁移顺序与回滚路径。

不要用大量类图替代决策理由。重要且难以逆转的选择应单独记录 ADR。

### 10. 用证据验证

按风险选择验证方式：编译期契约测试、单元/组件测试、依赖规则检查、并发压力测试、故障注入、基准、原型或兼容性实验。重点验证：

- 最重要质量场景是否达到指标；
- 边界是否阻止了不允许的依赖；
- 订阅、任务和服务在关闭时是否安全退出；
- 慢消费者、异常处理器、取消、重入和队列满时是否符合契约；
- 抽象成本是否由测量支持；
- 迁移过程是否允许旧路径与新路径受控共存。

仅完成文档评审时明确说明未进行代码、并发或性能验证。

## 执行架构评审

读取 [review-checklist.md](references/review-checklist.md)，按“驱动因素 → 边界 → 依赖 → 运行时语义 → 数据与消息 → 质量证据 → 演进成本”的顺序检查。将问题分为：契约缺失、已证实缺陷、风险、权衡和可选优化；不要把个人风格写成架构缺陷。

## 交付说明

让交付深度匹配任务范围。单个模式问题说明意图、适用条件、实现选择、权衡和简短示例即可；系统级架构设计再说明假设、最关键的三项驱动因素、推荐方案、主要替代方案、C++23 特性的实际收益、第三方或自研边界、验证证据以及尚未解决的风险。若建议抽取公共框架，列出首个真实消费者和第二个独立消费者；没有第二个用例时优先保留项目内实现。
