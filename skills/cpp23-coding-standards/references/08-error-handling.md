# 08 · 错误处理与诊断

## 适用范围与核心原则

先确定错误是否属于正常业务分支、可恢复失败、契约违反或异常执行路径，再选择返回类型。项目级异常策略和 ABI 边界优先。

## 选择错误通道

- 使用 `std::optional<T>` 表达“没有值”且无需区分原因的结果。
- 使用 `std::expected<T, E>` 表达调用方通常需要检查并可能恢复的失败。错误类型应稳定、可比较或可记录；
  简单工具使用 `std::string` 并非错误，但大型 API 通常受益于结构化错误类型。
- 对不适合逐层显式检查、但可由更高层边界统一处理的失败使用异常。异常不等同于“不可恢复”；真正不可恢复的
  内部不变量破坏通常应触发调试断言，并执行项目定义的快速失败策略。
- **禁止**让异常穿越 C ABI、不同运行库或项目明确禁止的边界；在边界捕获并转换成稳定错误表示。
- 不要使用输出参数组合 `bool` 表达普通返回结果，除非外部 ABI、性能测量或多结果接口确有要求。

## 异常与 `noexcept`

- 按 `const&` 捕获具体异常类型，避免切片。在线程入口、`main`、C ABI 或日志等顶层边界可以使用 `catch (...)`
  保证异常不越界，并保留可诊断信息。
- 仅当完整契约保证异常不会传播时标记 `noexcept`。若 `noexcept` 函数仍抛出，程序将调用 `std::terminate`。
- 析构函数和释放操作不得传播异常。`swap` 只有在所有交换操作均不抛时才应标记 `noexcept`。
- 禁用异常的构建中 `noexcept` 仍用于表达契约、参与类型系统和选择算法路径，不是“无意义”的标记。
- 复制并交换（copy-and-swap）可以提供强异常保证，但可能阻止复用现有存储。根据资源类型和性能要求选择，
  不作为所有赋值运算的强制模板。

## 诊断上下文

- 可用默认实参 `std::source_location::current()` 捕获调用位置。通常把位置参数放在末尾以便调用，
  但语言只要求默认实参规则成立，位置不会改变捕获语义。
- 可在非热路径使用 `std::stacktrace`。其可用性、链接要求、符号信息、性能和可能的分配失败必须按工具链验证。
- 记录错误时避免重复包装丢失原始原因。为错误链保留错误码、上下文和底层原因。

## 审查重点

- 检查每个失败通道是否可被调用方可靠地区分和处理。
- 检查异常安全保证：无泄漏、基本保证、强保证或不抛保证是否与实现一致。
- 检查跨线程、跨动态库和 C ABI 边界的异常是否被截获。
