# 12 · 可移植性、C++ 模块与 ABI

## 适用范围与核心原则

以项目声明的支持矩阵为准，而不是假设“C++23 模式”意味着所有库特性、调试设施和 ABI 都可用。

## 工具链与特性检测

- **必须**记录最低编译器、标准库、平台和构建选项。语言版本宏不能替代标准库功能测试宏
  （library feature-test macro）。
- 检查库特性时先包含定义该宏的标准头或 `<version>`。根据宏规定的版本值判断能力，不只检查是否定义。
- 对支持矩阵尚未完整覆盖的 C++23 特性，在一个兼容层中提供选择和替代实现。不要在业务代码散布平台分支。
- 不要使用日期式描述，例如“到某年仍不支持”；应引用项目实际测试矩阵或最低版本。
- 编译器扩展、内建函数和平台 API 应封装在窄边界中，并提供可测试的标准实现或清晰的不可用诊断。

## C++ 模块与头文件

- 采用 C++ 模块前验证编译器、生成器、依赖扫描、包管理、IDE 和增量构建行为。
- 模块接口单元（module interface unit）应只导出稳定 API。谨慎处理头单元、全局模块片段、宏和传统头文件之间的边界。
- 不要把 C++ 模块视为可移植性保证；它主要改变依赖表达与编译模型，ABI 仍由工具链和公开类型决定。

## ABI 与外部边界

- 跨动态库边界前明确编译器、标准库、运行库、分配器和编译选项是否一致。
- 避免在长期稳定的 C ABI 中暴露异常、C++ 标准库容器、模板、引用、类布局或由实现定义的枚举大小。
- 仅在双方共享兼容运行库与所有权协议时跨边界传递智能指针。否则使用不透明句柄和成对创建/销毁函数。
- 不要让异常穿越 C ABI。把错误转换为稳定错误码、结果结构或调用方提供的诊断通道。
- 序列化**必须**定义字节序、宽度、对齐、版本和验证规则。不要直接持久化对象内存布局。
- 使用固定宽度整数只解决宽度问题；仍需处理字节序、溢出和协议取值范围。

## 审查重点

- 检查使用的新特性是否确实被所有受支持工具链编译和测试。
- 检查公开符号、对象布局、异常和内存释放是否跨越不兼容边界。
- 检查平台条件编译是否集中、对称且具有不可用路径测试。
