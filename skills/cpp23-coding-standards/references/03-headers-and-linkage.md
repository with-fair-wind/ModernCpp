# 03 · 头文件、链接与 C++ 模块

## 适用范围与核心原则

保持接口自包含、定义唯一且依赖方向清晰。先保证正确性，再根据实际构建数据优化包含关系和实例化成本。

## 头文件与依赖

- **必须**让每个头文件在单独包含时可以编译，并直接包含其公开声明所依赖的定义。
- 项目应统一使用头文件保护宏（include guard）或 `#pragma once`。选择属于项目约定，不影响接口语义。
- 可对仅以指针或引用出现的项目类型使用前置声明，但不要前置声明标准库类型，也不要制造脆弱的跨组件声明。
- 需要完整类型的成员、基类、`sizeof`、内联成员访问和多数模板实例化必须看到完整定义。
- include 顺序和分组服从项目 `.clang-format`。不要为追求“最少 include”破坏头文件自包含。

## 定义、链接与命名空间

- **必须**遵守单一定义规则。不要通过宏让不同翻译单元看到不同的 inline、模板或变量定义。
- 仅在头文件定义跨翻译单元共享变量且语义合适时使用 `inline` 变量。需要稳定 ABI 或隐藏实现时可使用
  `extern` 声明和单一 `.cpp` 定义。应避免可变全局状态。
- 对仅供当前翻译单元使用的类型、变量和函数使用匿名命名空间。文件作用域 `static` 并非错误，但应保持项目一致。
- 不要在头文件的命名空间作用域使用 `using namespace`。局部 `using` 声明在不引入冲突时可以使用。
- 可使用内联命名空间（inline namespace）管理库版本，但必须评估符号名和 ABI 影响。

## 模板与常量求值

- **必须**让模板定义在发生隐式实例化的位置可见；这通常意味着放入头文件，但显式实例化可以把实现放在 `.cpp`。
- 使用显式实例化减少重复代码时，在头文件写 `extern template` 声明，并在一个翻译单元提供对应定义。
- `constexpr` 函数不因语言规则而必须位于头文件；只有需要跨翻译单元内联或常量求值时才需要暴露定义。

## C 与 C++ 模块边界

- 对自己声明的 C 语言链接函数使用 `extern "C"`。不要盲目在 `extern "C"` 块中包含已自行处理 C++
  兼容性的第三方头文件。
- 可在项目工具链、构建系统和依赖均稳定支持时采用 C++ 模块。不要仅为语法现代化混用多套模块方案。
- **必须**避免在模块接口单元（module interface unit）的导出声明中泄露非公开实现类型，并验证宏、头单元和
  传统头文件混用的行为。

## 审查重点

- 检查头文件是否依赖传递 include 才能编译。
- 检查显式实例化是否同时具有 `extern template` 声明和唯一实例化定义。
- 检查公开头文件、模块接口单元和动态库边界是否无意暴露实现或不稳定类型。
